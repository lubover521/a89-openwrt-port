# 屏幕内存增长与低唤醒修复（2026-10-11）

此修复覆盖仓库内共用移动屏幕的机型，不是T551M硬件专用补丁。
故障进程是设备本地的WPE WebKit网络子进程，不能据此认定电脑浏览器中的
LuCI看板、基带服务或所有无屏设备存在同一个泄漏。

## 覆盖范围

| 机型 | 构建与部署 |
| --- | --- |
| T551M | 共用屏幕构建入口已包含全部依赖；实机已部署并完成5分钟息屏观察；本地保存的ext4根镜像已同步 |
| 荣悦E5 | 调用同一屏幕构建入口；实机已部署并完成5分钟观察；日常离线root与TF打包root均已同步 |

E5的TF新包重新装配用户态根镜像，沿用原E5内核和boot，保留TF启动功能。
已发布的旧压缩包不原地修改，新的构建带独立名称、文件校验和与修复源码摘要。
实机采用仅更新8个相关文件的方式，保留网络、充电、CPU、音频硬件配置、NV和启动选择。

## 实现与省电原则

- 通话状态由已有观察器通过单个SSE连接推送，前端与电话子页面共享；
  变化时发送，空闲30秒心跳。移除健康连接下每350ms一次的重复HTTP查询。
- 其余本机JSON读取共用WebSocket，继续调用原接口，保留原来的刷新频率。
  插件通过SDK复用父页面连接。POST等控制命令不自动重试。
- 监听仅限127.0.0.1，严格验证Host/Origin；连接、并发请求及消息大小有界。
  空闲线程阻塞等待，不增加定时轮询、CPU高频策略或新的常驻进程。
- 断线回退原读取方式，恢复后停止重复轮询；保留取消请求、退出清理、来电亮屏、
  锁屏、防误触、通话时长、拨挂节流与DTMF等行为。
- 修复通过改变请求路径规避浏览器重复HTTP加载时的对象保留，未修改系统WebKit库；
  不是对底层引用生命周期问题已彻底修补的声明。

源码仍位于历史目录`devices/t551m/infoscreen/`，E5通过
`devices/e5/stage.py → devices/t551m/ui.py → infoscreen/stage.py`复用。
内部既有`T551M*`接口保留兼容，不作为机型开关，也不决定硬件参数。

## 验证

- `wsl -d Ubuntu-22.04 -- python3 openwrt/tests/screen-profiles.py`：在临时目录
  检查E5/T551M的HTML加载顺序、SDK/电话前端、后端依赖齐全。
- `call-events.py`、`screen-rpc.py`、`voice-audio.py`、`test_calls_transport.cjs`、
  `test_phone_browser.py --push`覆盖真实连接、200次读取、并发、取消、断线回退、
  控制命令不重发、旧快照不覆盖新推送及通话交互。
- T551M连续300.17秒息屏，网络进程匿名内存9064→9016KiB；相关屏幕进程与
  通话服务合计CPU约1.68%单核。25秒加速读取匿名内存+8KiB，旧HTTP方式约+1.4MiB。
  详细实验、原始记录和范围见[T551M现场记录](T551M-memory-investigation-20261011.md)。
- 两份E5离线root更新前后，认证、网络、热点、屏幕设置及功放程序摘要均一致。
  T551M离线镜像更新前后使用支持该镜像格式的e2fsck 1.47.2检查通过。
- 新E5 TF根镜像通过e2fsck检查，并从镜像内逐一读出8个相关文件核对，
  确认入口脚本、依赖和机型标记正确；boot摘要与原包一致，没有预装Docker。
- E5连续300.17秒，同一网络进程PID22952匿名内存8916→8888KiB。
  首个样本仍亮屏，随后6个样本均息屏；严格息屏250.15秒窗口为8872→8888KiB
  （+16KiB），Web进程−600KiB、通话服务不变，未复现此前持续大量增长。
  该息屏窗口屏幕相关进程及通话服务合计CPU约2.51%单核。两台机型的状态与
  硬件不同，不能据此比较续航。原始记录：`work/e5-port/memory-five-minutes.jsonl`。
- E5实机已核验7个源码文件摘要、入口加载顺序、两条本机长连接和通话观察器
  available=true。构建检查与模拟通话回归通过；本轮没有再次拨打真实电话，
  也没有重复执行实体TF卡首次安装。

短窗口观察不能代替整夜运行；未使用功耗仪测量，不能换算续航提升百分比。
