# T551M 屏幕网络进程内存增长现场

2026-10-11，连接 `192.168.9.1` 后以 `/etc/e5/device-profile=t551m` 确认目标。
内核 `6.18.54-t551m-otg10-g020b970e351e-dirty`，运行约18小时49分钟。
初始诊断阶段只读，保留了故障进程现场。用户随后要求修复并明确要求省电；
下文记录对照实验、修复与实机验证，不能将服务重启后的内存释放本身算作修复证据。
本修复现由E5/T551M共用，无屏机型不启动相关服务；跨机型部署与打包结果见
[统一修复记录](SCREEN-MEMORY-FIX-20261011.zh-CN.md)。

## 已确认

- 初始 MemTotal 1,533,228 KiB，MemAvailable 76,900 KiB。
- 屏幕浏览器 `WPENetworkProcess` PID17883：RSS 934,724 KiB，匿名
  927,964 KiB，约占物理内存61%。其父进程为屏幕使用的 Cog。
- `WPEWebProcess` 初始RSS 99,724 KiB，后续下降到约89MiB以下；
  `cp_diskserver` 54,508 KiB。内核不可回收Slab约63MiB，DMA-BUF约2.4MiB。
  当前大头明确是屏幕网络子进程，不能根据虚拟地址空间69GiB判断物理占用。
- 三次快照间隔0、31.14、107.70秒，网络进程RSS依次为
  934724、935188、936152 KiB，匿名内存927964、928400、929464 KiB。
  同一PID持续增长，文件描述符均26个，屏幕亮度0（息屏）。
- `/tmp/run/e5-infoscreen/.cache/wpe` 仅280KiB；smaps显示主要占用为
  private dirty anonymous。不是普通可回收文件页缓存占满内存。
- 实机软件版本：WPE WebKit2.50.1-r1，libsoup3 3.6.5-r1，Cog0.18.5-r1。
- 30秒只读环回抓取（仅统计HTTP方法与路径，不保存正文、号码或短信）：
  `/api/plugins/phone/live` 83次，`/api/status` 6次，`/api/update` 1次。
  同期网络进程RSS与匿名内存都增加408KiB。短时增长速度约47MiB/小时，
  不是对未来增长的保证。
- 实机calls.js与仓库SHA256一致，来电检测使用350ms间隔、请求完成后
  再安排下一次，带2500ms超时；没有发现这段代码同时无限创建并发请求。

## 结论与边界

已定位持续占用和增长发生在屏幕浏览器网络子进程。高频来电轮询是息屏时
占绝大多数的请求来源。最小页面与分配跟踪进一步确认重复HTTP读取伴随
持续保留的约4KiB对象；具体类型与未释放的引用路径尚未完全定位。
最终采用通话事件推送和共用长连接读取，避开反复创建浏览器HTTP加载器。
这是应用请求路径的修复，**不是已修补WebKit底层引用泄漏的声明**。

不能把停止轮询或定期重启浏览器算作底层分配器/网络库的根因修复。

## 请求路径对照

- 同一个旧网络进程，临时最小页面分别静止、fetch、fetch+AbortSignal、XHR，
  每组稳定后观察25秒，结束自动恢复屏幕；如果实际来电则提前恢复。
- 静止页面匿名内存932408→932400 KiB；fetch增加1432 KiB，带signal增加
  1352 KiB，XHR增加1400 KiB。因此简单替换请求API无效。
- 原生libsoup同步1200次请求，匿名内存5732→5744 KiB；原生异步1200次请求，
  第200次5864 KiB，第1200次5884 KiB。原生对照未复现浏览器的大幅增长。
  这缩小了范围，但还不足以认定某个WebKit对象或libsoup异步路径有引用泄漏。

## 省电与通话通知修复

- `e5-voice-audio` 内挂接 `e5_call_events.py`，使用已经得到的通话快照。
  没有新进程、额外AT/D-Bus查询，原观察器0.5秒刷新及D-Bus事件唤醒保持不变。
- `127.0.0.1:8089/events` 仅允许屏幕来源 `http://127.0.0.1:8088`，
  校验Host与Origin。事件与读取服务合计最多6个客户端，只保留最新状态，不积压历史队列。
  去掉每轮变化的updated时间戳后比较状态，变化才发送；闲置30秒心跳。
  accept线程用select等待，发送线程用Condition等待，没有高频空转定时器。
- `calls.js` 使用单个EventSource，shell和电话iframe共享通知。正常情况下
  取消每350ms的来电HTTP查询；推送失败恢复原350ms查询和2.5秒超时，
  推送恢复后停止回退查询，忽略较晚返回的旧查询结果。
- 电话界面仍在进入和用户操作后获取完整资料，通话状态改为订阅；
  保留时长、拨挂节流、等待通话ID超时，防止不再轮询后按钮不解锁。
  页面卸载释放订阅、连接和计时器。
- `stage.py` 同步携带推送模块，保证后续屏幕部署不会漏后端。无屏设备
  不启动这个监听端口。无需改变CPU调度、频率、NV、基带、Wi-Fi或屏幕状态刷新频率。

### 延长观察与进一步对照

- 300.2秒连续息屏，网络进程匿名内存9016→9312 KiB（+296 KiB），仍有剩余增长，
  不能将上面30秒无增长窗口解释为完全修复。同期可用内存约987→989 MiB。
- 按进程CPU累计时钟差值折算单核占用：网络进程约0.117%，Web进程约0.476%，
  Cog约0.113%，Cage约0.043%，屏幕uhttpd约0.027%，已有通话服务约0.933%。
  这是修复后的息屏实测值，没有同条件旧版CPU样本，不能推出CPU或续航改善百分比。
- 重复25秒快速fetch对照：默认缓存+1384 KiB，document-viewer+1420 KiB，
  `Malloc=1`系统分配器+1360 KiB，均未消除增长。无效配置不应进入最终版本。
- LD_PRELOAD分配跟踪与现有图形/浏览器栈不兼容，启动失败；已恢复原session和
  网络进程原始可执行文件，校验原二进制SHA256，移除跟踪库。未改系统libc或WebKit库。
- 后续使用临时eBPF uprobes跟踪指定网络进程的分配/释放，不保存HTTP正文。
  采集完成关闭perf/BPF文件描述符并删除专用事件；这些探针不随固件发布或常驻。

### 分配跟踪与长连接读取

- 临时使用系统分配器以便跟踪内部对象，两轮25秒快速读取分别保留471、474个
  4224字节对象，合计约1.90、1.91MiB。主要分配调用链与对象虚表位于WPE WebKit库；
  结合源码结构疑似NetworkResourceLoader，但剥离符号的实机库不能完全确认类型。
  不把猜测的类型当作已证实根因，也没有据此修改系统动态库。
- 新增`e5_screen_rpc.py`，与现有通话事件服务共用监听端口，屏幕经
  `ws://127.0.0.1:8089/rpc`读取本机JSON接口。后端固定访问127.0.0.1:8088，
  仅GET；最多4个工作线程、8个在途请求，每条消息及响应大小有上限。
  空闲时阻塞等待，不增加轮询、缓存、定时重启或新的常驻进程。
- `transport.js`仅接管本地`/api/`字符串GET及普通method/cache/signal选项。
  POST、上传、自定义headers及其他fetch选项保留原生行为；不重试控制操作。
  GET失败可回退原生请求；主动取消和页面卸载不重发。插件SDK共用父页面连接。
  原status、update、流量等刷新频率不变，后端读取仍获取同一接口的最新结果。
- `openwrt/tests/screen-rpc.py`使用真实浏览器与HTTP后端验证200次连续读取、
  并发完成顺序、HTTP错误、带自定义header的原生请求、POST仅执行一次、
  取消不重发、断线回退及及时关闭；通过。新传输与真实推送同时启用的电话
  浏览器回归也通过，无JS错误。
- 实机25秒相同快速fetch页面，新传输匿名内存8932→8940KiB（+8KiB），
  同一网络进程PID31065；旧HTTP方式约+1.4MiB。结束后自动恢复主页。
- 本次只更新T551M的屏幕JS和通话服务附属Python模块，目标文件更新前均保留
  本地原件；未改NV、CPU调度、内核、启动分区或其他已连接机器。

### 最终息屏验证

- 长连接读取与事件推送同时启用，连续300.17秒、7个样本均为亮度0，
  网络进程PID31065保持不变。匿名内存9064→9016KiB（−48KiB），
  结束RSS60328KiB（约58.9MiB）；不再复现此前线性增长。
- 同期Web进程匿名内存55260→54640KiB，通话服务19712→19700KiB，
  屏幕HTTP服务504→504KiB；没有把持续增长转移到另一个已观察进程。
  系统MemAvailable从1010172增至1015484KiB（约991.7MiB）。
- 单核CPU时间占比：网络进程0.043%、Web进程0.460%、Cog0.077%、
  Cage0.047%、屏幕uhttpd0.037%、通话服务1.016%；所列进程合计约1.68%单核。
  SSE单独版本对应合计约1.71%，新读取桥没有在此窗口显示明显CPU负担增加。
  这不是整机CPU/功耗测量，也不能换算续航提升百分比。
- 实机文件长期保存，后续staging包含全部新增依赖。最后补齐自定义fetch选项
  和跨来源iframe兼容保护后重载屏幕；不安排任何周期重启或常驻诊断任务。
- 25秒加速读取与5分钟正常息屏是本轮实际覆盖的内存观察范围，尚未做整夜验证。
  少量原生控制请求、页面导航和断流回退仍会使用WebKit HTTP路径，底层对象
  生命周期问题并未由本次应用层修改直接修补。
