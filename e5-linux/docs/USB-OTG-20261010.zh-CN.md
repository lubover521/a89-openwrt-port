# T551M / E5 OTG 枚举故障调查（2026-10-10）

## 现象和实机证据

用户报告两台设备的屏幕均不提示 OTG 外设，USB 网卡也无法给电脑分配 IP。
本轮最先连接并验证身份的是 T551M（ARJ11X，原运行 CPU5 内核及 WiFi4 模块）；
E5 尚未在本轮实测。没有让管理电脑连接热点。

T551M 的 USB 策略为 auto，USB 网卡自动加入 LAN 已启用，常用网卡驱动已加载。
插拔采集显示 Type-C 检测到 source，OTG regulator 启用，MUSB 注册主机总线；
随后反复打印 `trying to suspend as a_idle while active`，峰值约每秒 3.1 万次。
USB 外设多次尝试以高速枚举，未形成可用网卡接口，稍后还出现 Babble。
因此本轮故障在 USB 主机/枚举层，屏幕提示和 DHCP 缺失是后续表现。

私有证据：`work/t551m/otg-regression-capture.jsonl`、
`otg-regression-before.txt`、`otg-regression-after.txt`。

## 共用启动路径修正

原厂 `musb_host_start()` 曾调用 `musb_start()` 完整初始化控制器。
移植后的 `hops.host_start` 没有实现，调用被空指针检查跳过；平台末尾只调用
`sprd_musb_enable()` 设置 SESSION/HOST_FORCE_EN。`musb_host_setup()` 注册 HCD
并不等于恢复 POWER 和中断掩码，而当前双角色配置下，虚拟 root hub 的
POWER 请求也不会执行 `musb_start()`。这使主机启动依赖上一角色遗留的寄存器状态。

`devices/t551m/usb_host.py` 现对共用的 `musb_sprd_otg_start_host()` 补齐：

- 重置 FIFO 后先确定平台角色为 HOST。
- 持锁设置主机状态、清除 gadget softconnect 影子，进入 A_WAIT_BCON。
- 调用现有 `musb_start()` 恢复 POWER、端点/总线中断以及 SESSION。
- 解锁后唤醒 root hub，继续外设枚举。

T551M 和 E5 的独立构建均调用此补丁；没有更改 CC 识别、充电电流、充电器
检测、DMA 传输或 LAN 配置。新构建分别为 `t551m-otg8` 和 `e5-mobile2`。
这不是关闭全局 USB 省电，也没有新增常驻轮询恢复服务。

`test_usb_host_start.py` 编译执行实际主机启动代码片段和核心 `musb_start()`，
检查冷启动、遗留 gadget 和挂起寄存器状态下的 POWER/IRQ/SESSION 恢复。
两种设备构建通过，充电转换/BC1.2 回归及 WiFi 发送路径检查通过；实物枚举、
DHCP 和反复角色切换仍须以部署后的测试为准。

## 部署期间的 F2FS 恢复

T551M 写入新启动镜像并正常重启后，userdata 的 F2FS 拒绝挂载：
`SIT is corrupted node# 10406 vs 6687`，检查点标记为 clean-unmount。
机器进入 initramfs 救援环境，USB 网卡地址为 192.168.77.1；串口确认仍是
T551M / ARJ11X，不能把这一地址误判为 E5 或 MU300。

在 userdata 未挂载时，先用块设备只读保护运行 fsck dry-run，将日志和
分区头部 64 MiB 保存到本地（这是元数据取证，不是完整数据备份）。随后离线
修复 F2FS，退出码 1；再次开启块设备只读保护复查，SIT/NAT/节点计数等全部
通过，无 Fail/ASSERT。以只读 norecovery 挂载后，OpenWrt ext4 镜像的
`e2fsck -fn` 五阶段检查通过，无需修复。只读核对设备配置、默认 Linux、
新模块目录及 `auto_work_mode=152` 均仍存在。

此次 F2FS 损坏根因尚未确认，不能归因于 OTG 修复，也不能宣称已永久解决。
未修改物理 NV。恢复记录位于 `work/t551m/f2fs-otg8-*.log` 和
`work/t551m/ext4-otg8-before.log`。启动镜像回退副本位于设备
`/mnt/e5-data/e5linux/otg8-rollback/boot-cpu5-wifi4-head.img`；刷写只覆盖 boot_b
前 56 MiB，保留启动日志区域，TF 启动 init 与既有发布镜像逐字节一致。

恢复后 T551M 已进入 `6.18.54-t551m-otg8-g020b970e351e-dirty` 的正常 OpenWrt。
WAN 已连接、热点 AP 及屏幕服务运行，USB NCM 管理连接正常，原始九个 NV
分区及隔离工作设备只读验证通过，CPU 电压配置仍为 `[0,0,0]`。插拔采集已
重新开启，等待修正版实物网卡结果。E5 的 mobile2 镜像已构建，尚未刷入实机。

## OTG8 实测未通过：重复注册 HCD

用户反馈三次插拔仅一次识别。完整日志实际记录四段 host 会话（含首次接入），
每段开头仍有约三秒、每秒约三万次 `a_wait_bcon while active` 挂起重试；
其中一段识别了 USB hub 和 Realtek 网卡，`r8152` 创建 eth0、加入 br-lan，
随后 carrier on。其余会话未完成枚举。说明单独补齐核心启动并不足以解决。

继续核对发现 `musb_init_controller()` 在 MUSB_OTG probe 时已经调用
`musb_host_setup()`，SPRD 角色 worker 在每次进入 host 时却再次调用。
同一个 `usb_hcd` 被重复传入 `usb_add_hcd()`，旧 root hub 没有注销。
实机回到电脑模式后仍残留 sysfs `usb1`，其 `busnum` 和 uevent `BUSNUM`
却为 2，设备节点为 `bus/usb/002/001`，证明 HCD 的总线身份被后一次注册覆盖。
这也让旧 root hub 的电源管理仍作用于同一个控制器。

OTG9 / E5 mobile3 在保持核心初始化修正的基础上：

- SPRD 的双角色端口在 probe 时只初始化 gadget，HCD 注册交由角色 worker。
- `musb_host_setup()` 对已注册的 root hub 不再重复注册。
- `musb_host_cleanup()` 对尚未注册或已清理的 HCD 不再重复移除。
- 非 SPRD 平台和 host-only 端口保留原先 probe 注册行为。

新增 `test_usb_host_lifecycle.py` 执行实际 probe 分支及 setup/cleanup 函数，
覆盖五轮插拔、重复通知、注册失败、gadget 初始化失败，以及其他平台/单角色
模式。两种设备构建及测试通过。旧 OTG8 不应被标记为已修复或发布为稳定版。
原始三次插拔反馈对应日志保存在 `work/t551m/otg8-three-replugs.txt`。

T551M OTG9 已刷入并正常启动。电脑模式下 `/sys/bus/usb/devices` 为空，
不再残留 probe 时创建的 root hub；USB gadget/NCM 正常、WAN 已连接，
本次 F2FS 和 ext4 正常挂载，无需再次修复。实物三次插拔测试已请求，
采集已启动；稳定性结论仍待这轮结果。E5 mobile3 已编译、打包，尚未部署。

### OTG9 复测：仍未通过

用户反馈“没效果”。`work/t551m/otg9-replugs.txt` 中两段主机会话均正确注册为
bus 1，不再重复注册，但仍出现每秒约三万次 `a_wait_bcon while active`。
外接第一层 hub 连续以 device 2/3/4/5 尝试枚举，均未完成；没有创建 r8152
网卡。Windows 曾显示有线端口 Up 和既有租约，不能据此判断本轮 DHCP 成功。

进一步检查发现 `musb_bus_suspend()` 在检查 active 状态之前就调用
`musb_port_suspend(true)`，可能在返回 EBUSY 前已经改写 POWER.SUSPENDM；
USB hub 的默认 autosuspend delay 为 0，会让拒绝挂起持续立即重试。
暂以仅本次运行的 usbcore autosuspend=-1 配合 MUSB trace 做对照诊断，
十五分钟后自动恢复，不将关闭全局 USB 省电写入固件。是否为枚举失败主因
仍需对照结果，不能把消除重复 HCD 等同于修复 OTG。

## 自动休眠对照成功与 OTG10 / E5 mobile4

用户回复“正常”。实际日志记录三轮 host 会话：每轮均识别 hub、r8152 网卡、
加入 br-lan 并出现 carrier；最后一轮 DHCPREQUEST/DHCPACK 明确给电脑分配
192.168.9.43，不是只看旧租约。期间没有 busy-suspend 重试风暴。
证据为 `work/t551m/otg9-pm-disabled.txt` 和对应 `.trace`。

已停止临时 trace，将 usbcore autosuspend 恢复为原来的 2 秒。永久候选方案
仅对 SPRD HCD 注册成功后的 root hub 调用 `usb_disable_autosuspend()`。
原因是 SPRD glue 在整个 host 会话本就持有控制器 runtime-PM 引用，主机
电源由角色 worker 管理；额外的 root-hub 自动挂起与它的启动状态冲突。
不修改全局参数、不改变下游设备各自的 autosuspend，拔出时依旧清理 HCD，
关闭供电并释放控制器电源引用。该策略不改变无 OTG 时的待机路径。

生命周期测试新增 SPRD root-only PM、重复通知、失败注册不得访问 root hub、
非 SPRD 原行为等断言，两棵内核通过；充电角色转换回归和完整构建通过。
T551M 版本为 `6.18.54-t551m-otg10-g020b970e351e-dirty`，E5 为 mobile4。
T551M boot_b 前 56 MiB 及匹配模块已安装并校验，保留启动日志尾部；
旧 OTG9 启动副本保存在设备 `otg10-rollback/boot-otg9-head.img`。
TF / 默认 Linux 的 init 与 OTG9 完全一致。候选方案仍需确认“仅 root hub”
策略下的实物插拔；E5 尚未部署。
